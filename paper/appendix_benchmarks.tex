\section{Benchmarks, Data Splits, and Runtime Settings}
\label{app:benchmarks}

This appendix documents (i) the public benchmarks used in every domain,
(ii) the exact pool/held-out sample counts we draw from each benchmark,
(iii) the per-pipeline runtime knobs (episode caps, token budgets,
parallelism), and (iv) the few-shot transfer protocol that consumes the
held-out manifests at gate stage~3a. All ID lists are released alongside
the code as deterministic stratified manifests
(\texttt{cold\_start/evaluation\_dataset/}, seed $=0$) together with a
\texttt{manifest.json} carrying SHA-256 hashes for every file, so that
all numbers below are reproducible and tamper-evident.

\subsection{Domain roles: source vs.\ transfer targets}
\label{app:bench-roles}

We split the five domains into one \emph{source} domain---games, in
which skills are first discovered and stress-tested---and four
\emph{transfer-target} domains, into which game-learned skills are
adapted few-shot at gate stage~3a. The asymmetry is hard-coded in
\texttt{common/enums.py}:
\begin{itemize}
  \item \textsc{Source}: \texttt{gymv} (13 retro Gym-Retro/Temporal
        environments).
  \item \textsc{Transfer target}: \texttt{browser}, \texttt{osworld},
        \texttt{video}, \texttt{visual\_reasoning}.
\end{itemize}
Volume is therefore deliberately unbalanced: the source pool is sized
for trajectory coverage, the target pools for \emph{stratified
diversity} so that every candidate skill, when probed at stage~3a, can
find $K\!\in\![5,16]$ relevant few-shot demonstrations in each target
domain. We do \emph{not} sweep full benchmarks on the target side---the
goal is transferability, not population accuracy.

\paragraph{Stratification axis.}
Each transfer-target slice is sampled by deterministic round-robin over
a benchmark-specific axis, so the pool over-samples rare buckets
relative to natural frequency---which is what we want for a few-shot
transferability probe (Table~\ref{tab:bench-strata}). Every category
that appears in the pool also appears in the held-out half, with a
proportional within-bucket split so any bucket containing $\geq\!2$
sampled items contributes to both halves.

\paragraph{Other invariants.}
\begin{itemize}
  \item \textbf{Headless by default} for BrowserGym (Xvfb-backed
        Chromium) and OSWorld (KVM guest); pass \texttt{--no\_headless}
        when debugging.
  \item \textbf{Frames are not saved} by default; \texttt{--save\_frames}
        persists every PNG fed to the VLM under
        \texttt{<run>/<task>/frames/ep\_NNN/step\_NNN.png}.
  \item \textbf{Reasoning-model detection} is regex-based
        (\texttt{\_is\_reasoning\_model}); matches route to
        \texttt{max\_completion\_tokens} automatically.
  \item \textbf{Resume is on by default}: episodes that already have an
        \texttt{episode\_NNN.json} on disk are skipped, which
        guarantees byte-identical reruns.
\end{itemize}

\paragraph{\texttt{reasoning\_effort} policy.}
The teacher's hidden-thinking budget is set per pipeline because the
SFT student (\texttt{Qwen/Qwen3.5-9B}) only learns from the visible
\texttt{<state>} block and action JSON---hidden tokens never reach the
trained policy.
\begin{center}
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Pipeline} & \texttt{reasoning\_effort} & \textbf{Rationale} \\
\midrule
\texttt{gymv} (source-domain trajectories) & \texttt{minimal} & structured extraction; student cannot use thinking \\
BrowserGym / OSWorld trajectories          & \texttt{minimal} & schema $+$ constrained action; the schema \emph{is} the planning surface \\
Visual reasoning MCQ (image $+$ video)     & \texttt{medium}  & teacher answer correctness is the bottleneck on multi-hop QA \\
\bottomrule
\end{tabular}
\end{center}
A paired smoke test ($n=5$ MiniWoB tasks) confirms this empirically:
\texttt{minimal} hit $5/5$ vs.\ \texttt{medium}'s $4/5$, with
$2.1\times$ lower wall-clock per step ($14.8$\,s vs.\ $31.5$\,s).

\subsection{Few-shot transfer protocol (gate stage~3a)}
\label{app:bench-fewshot}

Held-out items are consumed only by the few-shot adapter
(\texttt{harness/few\_shot\_adapter.py}) at gate stage~3a, never during
cold-start data generation. The adapter is stateless: given a
\texttt{SkillRecord}, a target domain, and a sequence of
\texttt{FewShotDemo}s, it (i) validates eligibility, (ii) coerces each
demo's \texttt{state} into a target-domain \texttt{StateSchema},
(iii)~runs the skill via \texttt{SkillHarness.run\_skill(\dots)}
against the registered adapter, (iv) scores each shot, and (v) returns
an \texttt{AdaptResult\{success\_rate, n\_success, n\_total, episodes,
\dots\}}.
\begin{center}
\small
\begin{tabular}{@{}lc@{}}
\toprule
\textbf{Knob} & \textbf{Default} \\
\midrule
\texttt{k\_shot\_default} (per skill per target domain) & $5$  \\
\texttt{k\_shot\_max}                                   & $16$ \\
\texttt{transfer\_min\_target\_domains\_verified} (PASS) & $1$ \\
Stage-3a verdict $\to$ \texttt{LIMITED\_PASS} threshold & $\geq 1$ verified target \\
Stage-3a verdict $\to$ \texttt{FAIL} threshold          & $0$ verified targets \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Cost ledger for one full cold-start pass}
\label{app:bench-cost}

GPT-5 reasoning-class pricing ($\$1.25$ / M input, $\$10$ / M output
incl.\ thinking). The lean plan above costs $\sim$$\$200$ per full pass
and dominates as follows: BrowserGym $\approx\!31\,\%$, OSWorld
$\approx\!28\,\%$, visual reasoning $\approx\!22\,\%$,
\texttt{gymv} $\approx\!18\,\%$. The two largest levers are
(a) \texttt{reasoning\_effort} (\texttt{medium}$\!\to\!$\texttt{minimal}
on env pipelines saves $\sim\!70\,\%$ of the bill) and (b) OSWorld KVM
concurrency (2$\!\to\!$8 guests collapses wall-clock from
$\sim\!6$\,h to $\sim\!0.8$\,h at the post-cut pool size).
\textbf{Update (2026-05-03):} the OSWorld pool was reduced from $250$
to $120$ stratified tasks (and the held-out from $50$ to $30$); all
$11$ snapshot buckets remain represented in both halves. This drops
the OSWorld cost share from $\approx\!45\,\%$ to $\approx\!28\,\%$
and the per-pass total from $\approx\!\$260$ to $\approx\!\$200$,
freeing budget for the WorkArena suite (browser-domain compositional
tasks, queued for the next pass).

\subsection{Reproducibility}
\label{app:bench-repro}

\begin{itemize}
  \item \textbf{Sampler seed:} $0$, with per-benchmark sub-seeding so
        that adding or removing one benchmark does not reshuffle the
        others.
  \item \textbf{Pool/held-out manifests:} checked in at
        \texttt{cold\_start/evaluation\_dataset/\{pool,holdout\}/} as
        plain text (one ID per line, comment header records
        \texttt{count}, \texttt{seed}, per-axis distribution).
  \item \textbf{Integrity:} \texttt{manifest.json} carries a SHA-256
        per file; \texttt{load\_manifests.verify\_integrity()}
        re-hashes every file at consumer start-up and fails loudly on
        drift.
  \item \textbf{Disjointness:} $\text{pool}\cap\text{held-out}=\varnothing$
        is asserted at build time for every benchmark; the per-axis
        bucket distribution is also written to
        \texttt{\_axis\_distribution.json} as a checked-in diagnostic.
  \item \textbf{Byte-stability:} re-running
        \texttt{cold\_start/evaluation\_dataset/build\_pool\_and\_holdout.py}
        on the same upstream dataset versions reproduces the same
        bytes (verified at build time).
\end{itemize}
